Architecture

What you'll find here: The main processing components that turn a user's message into a support result.

Matching model

The current design separates understanding into four conceptual signals:

SignalPurpose
IntentWhat the user is trying to do.
ObjectThe application, feature, device, or thing involved.
ContextAdditional details that help distinguish similar support topics.
StateA relevant condition or status that can further distinguish a support topic; it may be empty.

Conversation state

Temporary conversation state is isolated by conversationId. The MVP tracks misses, repeated ambiguity, unresolved-question details, pending submissions, answered questions, and whether it is waiting for helpfulness feedback. This prevents one active conversation from sharing state with another.

Unresolved issue records

When a problem is submitted for IT review, the chatbot preserves both the original question and the later rephrased or clarifying question. Local Agents Playground testing records the user as user. A future Microsoft Teams deployment will obtain the user identity from the authenticated Teams environment.

{
  "conversationId": "...",
  "user": "user",
  "originalQuestion": "...",
  "rephrasedQuestion": "...",
  "submittedAt": "2026-09-15T14:03:22.892-07:00"
}

Submission timestamps use ISO 8601 local runtime time with the UTC offset. Unresolved records remain separate from approved support knowledge.

Knowledge separation

Approved support content and semantic matching vocabulary are kept separate. Unresolved user submissions are also kept separate and must be reviewed before becoming approved support knowledge.

MVP boundary

The current milestone proves the core support workflow locally. Production Teams deployment, organizational authentication, Pub/Sub, automated weekly notifications, database-backed knowledge, and production monitoring remain outside the MVP.
